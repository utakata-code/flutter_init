## [2026-07-11] utakata_studio 白紙化と CLI 改善方針の策定・実案件フローとの統合検討

**ステージ**: 改善計画フェーズ（リポジトリ本体）
**担当AIエージェント**: Claude Code（Fable 5）
**ブランチ**: dev

### 🎯 目的・背景

- utakata リポジトリは「AIと人間の際限のない共作」を目的に作られたが、開発者は実際に**受託案件**（ココナラ経由・パパママお知らせHIKYAKUBIN）で活用しており、実態は**「お客様・人間・AI」の三者共作**である。
- 現状のテンプレート（`.agent/` + `AI/`）は開発者⇔AI の二者を想定しており、実案件で発生するクライアントとのやりとり・合意管理をカバーしていない。
- この乖離を埋めるため、実案件で使っている `doc/` ディレクトリ構造とテンプレートの統合を検討する。

### ✅ 実施した作業

1. **リポジトリ全体調査** — utakata_code（CLI, v0.5.8）と utakata_studio（Flutterアプリ, v0.1.0+1）を並行調査し、課題を洗い出した（要点は下記「発見した問題」）。
2. **utakata_studio の白紙化** — studio は本来の目的（アーキテクチャのローコード編集）が未着手のまま読み取り専用ビューアに留まっていたため、**白紙に戻す決定**。`dev` ブランチを作成・切替のうえ `packages/utakata_studio/` をディレクトリごと削除（ステージ済み・未コミット）。今後は **utakata_code の改善に専念**する。
3. **実環境の再現** — `example/` ディレクトリで `utakata create example_app` を実行し、テンプレートファイルが実在する状態を作成。初回実行は build_runner ステップで失敗（Flutter 側の iOS ephemeral シンボリックリンク問題）、`flutter clean` → `pub get` → `build_runner` の手動再実行で復旧。
4. **実案件 doc/ の持ち込み** — 別プロジェクト（受託案件）で使用中の `doc/` を `example/example_app/doc/` にコピーし、現在のフローを調査・確認した。

### 💬 会話の要点（現状フローの確認）

**テンプレート想定フロー（`.agent/skills` 4スキル + `AI/`）**
- `flutter-development-guide`（モード選択・全体案内）→ Stage 1 仕様策定（`AI/specs/application_specification.md`）→ Stage 2 構造計画（`AI/specs/structure_plan.md`）→ Stage 3 レイヤー別実装。
- 登場人物は開発者と AI の二者。記録は `AI/logs/conversation_log.md` に集約する想定。

**実案件の運用フロー（`doc/`）**
- `doc/案件整理サマリー.md` — 案件の単一情報源（契約条件・機能一覧・クライアント合意履歴を日付/金額つきで管理）
- `doc/archive/見積もり提案書.md` — 契約前フェーズの成果物
- `doc/log/raw/` — **お客様との会話**の生ログ（日付別）
- `doc/log/post_contract_summary_*.md` — 生ログの期間別サマリー（`<!-- raw: ... -->` で出典行番号を付与）
- `doc/log/impl/` — 機能単位の実装計画書（テンプレートあり。「utakata diff ゼロ維持」の記述があり、現場側から CLI へ既に接続済み）。完了後は `archive/` へ移動
- `doc/guides/` — 案件横断の再利用ナレッジ（store/payment/infrastructure/testing/troubleshooting）+ 案件固有ガイド（project/）

**ログの棲み分け（現在の運用）**
- `AI/logs/conversation_log.md` = **開発者と AI の会話**
- `doc/log/raw/` = **お客様との会話**

### 🔍 発見した問題

**utakata_code（CLI）の主な課題**
- `plan` ⇔ `diff`/`validate` の構造変換（`direct` のネスト/フラット化）が脆く、最重要ロジックが未テスト
- 作者メモ（旧 TODO_05.md）記載の保留バグ: `feature init` が `__files__` を無視 / `validate`・`diff` の誤検知4件（`*.freezed.dart`・`*.g.dart` の誤判定、`exceptions/` への親規則適用、dart ファイルの `__files__` 誤認、feature 名プレフィックス誤検知）
- `command_runner.dart` のバージョンハードコード、ケース変換関数の重複実装（4ファイルで挙動差あり）、自作 YAML シリアライザのエスケープ欠如、`catch (_) {}` の握りつぶし多数
- `project_status` 出力の日本語ハードコード（`UTAKATA_LANG` 無視）
- 非推奨の `AI/scripts/*.sh` が生成プロジェクトに同梱され続けている（Stage 3 スキルの「事前準備」も旧スクリプトを案内したまま）
- `utakata status` の `flutter analyze` が `build/` 配下まで解析し、本来の状態が埋もれる
- `.agent/` のモード2/3（既存アプリ開発）が TODO のまま未実装

**テンプレートと実運用の乖離**
- クライアントという第三の当事者、契約前フェーズ、合意トラッキング、生ログ→サマリーの2層ログ、機能単位の実装計画書、案件横断ナレッジ — いずれもテンプレートに存在しない
- 記録系が二重化（`AI/logs` と `doc/log`）
- 実要件はクライアント⇔開発者の会話（`doc/log/raw/`）にあるが、仕様書への反映経路が仕組み化されていない

### 💡 決定事項・検討中の方針

**決定事項**
1. utakata_studio は白紙に戻す（dev ブランチで削除済み）。utakata_code の改善に専念する。
2. `doc/` の現構造は洗練途上であり、AI 側（`AI/` テンプレート）の構造も踏まえてブラッシュアップを行う。
3. 統合検討の場として `example/example_app`（テンプレート実物 + 実案件 doc/ のコピー）を使う。

**検討中の方針（開発者の課題感）**
1. **編集するファイルと編集しないファイルの区別** — テンプレートには2種類のファイルがある:
   - 編集不要: ガイド・ナレッジ・アーキテクチャ説明の `.md`（GUIDE.md 等）
   - 要編集: `feature_request.yaml` などプロジェクトごとに編集が必要なファイル
   - 現在は案件ごとに git 管理しており、編集しないほうがいいファイルも変更できてしまう。対策として**別 git での管理、もしくは読み取り専用化**を検討中。
2. **ナレッジとロジックの分離** — さらにナレッジは2層に分かれる:
   - テンプレートとして用意している（案件非依存の）ナレッジ
   - そのプロジェクト固有のナレッジ
3. **スナップショット方式の廃止と常時監視サーバー構想（utakata コマンド再編の起点）**
   - **課題**: `feature_request.yaml` からの `plan` 生成は良いが、
     - ファイル名をフルで指定しない（`__files__` は命名が決定的な場合のみ生成される）
     - **後からの変更に弱い**。生成後にファイルを追加したくなったら YAML 側を編集して計画に反映する、という双方向のメンテナンスが必要になっているのが実態
   - **構想**: `lib/` 以下の dart ファイルを**常に監視するローカルサーバー**を立て、実際の構造を完全に動的へ反映させる
     - 常に「現在の状態」が分かるため、`utakata scan` でスナップショット（`current_structure.yaml`）を撮る必要がなくなる
     - この前提に立って **utakata のコマンド体系を再編**したい（scan/snapshot 系の廃止・統合を含む）
   - ※ 他にも課題あり（次回以降に記録を継続）
4. **feature ごとの実装計画の強制（推奨フローへの組み込み）**
   - **課題**: 現在のフローは「仕様書 → 構造計画 → 実装」だが、規模が大きくなると feature ごとに実装計画を書くことが実際に発生している。現在は仮置きで `doc/log/impl/` に配置している状態
   - **構想**: utakata が推奨する実装手順として、**feature を計画したら feature ごとの実装計画の作成を強制**する
     - 実案件の `doc/log/impl/_実装計画書テンプレート.md`（出典・合意の区別、変更ファイル一覧、utakata diff ゼロ維持等を規定）が下敷きになる
5. **お客様との会話管理の構造化と utakata コマンド化**
   - **課題**: 現在は妥協として `doc/log/raw/` 配下におおまかな日付ごとの生ログ（.md）を置いているだけ
   - **構想**:
     - 会話データは **JSON または YAML で構造管理**し、プレビューを `.md` として生成する（project_status.yaml + preview/*.md と同じパターン）
     - **`utakata log add ""` のようなコマンド**で、日時・発言者・内容を記録できるようにする
     - **役割分担（決定）**: 記録は**人間がコマンドで行い**、**AI エージェントは読み取り専用**として要件・合意の情報源に使う
6. **AIエージェント統合の Claude Code 前提化**
   - AIエージェントとの共作は、現在最も強い **Claude Code を想定**して整備する
   - 具体的には**サブエージェント定義・スキル・フック（hooks）の整備**（汎用の `.agent/` から Claude Code のエコシステムへの対応）
7. **よくあるパターンの feature テンプレート（プリセット）**
   - **構想**: `auth` feature、`payment` feature など、頻出パターンの feature を**丸ごとテンプレートとして用意**しておけば、基本コピペで再利用性が上がる
   - コマンド例: `utakata feature add --template <id>` のような形でプリセットから feature を生成する
