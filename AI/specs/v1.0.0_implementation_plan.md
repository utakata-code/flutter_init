# utakata v1.0.0 実装計画書

作成日: 2026-07-19
入力: `v1.0.0.md`(コンセプト)、`v1.0.0_review.md`(レビューと追記群)、現行コードベース(旧v0.6〜v1.1の再設計完了状態、pubspec は 1.0.0 に変更済み・未リリース)

## 0. 全体方針(実装者判断で確定した設計決定)

レビューでの議論を踏まえ、以下を本計画の前提として確定する。

| # | 決定 | 理由 |
|---|---|---|
| D1 | **Single Source of Truth は `utakata_arch_lib`**。utakata パッケージの `lib/src/0_templates/` は、リリース時に arch_lib からスクリプトで同期される「同梱コピー」に位置づけを変える | デフォルト経路は今まで通りオフライン(pub cache)で動き、かつ内容の二重管理を防ぐ |
| D2 | **リモート参照はオプトイン**。`utakata.yaml` の `knowledge_repo.url` を明示した時だけフェッチが動く。デフォルト(未指定)は同梱コピーを使い、ネットワークに一切依存しない | レビュー①への回答。受託のオフライン環境を壊さない |
| D3 | **フェッチ結果は lockfile(`utakata.lock`)でコミット SHA 固定** | サプライチェーン注入・再現性喪失への最小対策。`--update` した時だけ SHA が動く |
| D4 | **`.claude/skills/` への書き込みは managed マーカー方式**。utakata が書くファイルには必ず origin コメントを付け、マーカーの無い(=人間が作った/編集した)ファイルは絶対に上書きしない | レビュー②への回答。`guide eject` と同じ「上書きしない」思想 |
| D5 | **セッションログ取り込みは人間駆動コマンド**。AI は `doc/records/` に書けないという既存原則(deny ルール)をそのまま維持し、取り込みは人間が `utakata log import` を叩く | レビュー⑥再訂正への回答 |
| D6 | **`utakata.yaml` をマスター設定に昇格**。`plan.yaml` の `project.architecture` は後方互換として残すが、両方あって食い違う場合は utakata.yaml が勝ち、警告を出す | v1.0.0.md §2 の中枢化。責務は utakata.yaml=プロジェクト全体の座組、plan.yaml=feature の意図、で分離 |
| D7 | **段階バージョン方式(2026-07-19 ユーザー決定で変更)**。未リリースの再設計内容は 0.6.0〜0.11.0 として CHANGELOG に段階のまま残し、本計画の各ステージも 0.x を刻む: S1→0.12.0、S2→0.13.0、S3→0.14.0、S4→0.15.0、S5→0.16.0、S6→0.17.0。**1.0.0 は S7(一般リリース)の時だけ**。いきなり 1.0.0 にするとバグ修正のたびに 1.0.x が消費されるため、安定化までは 0.x に留める | ユーザー決定 |
| D8 | **スコープ外**: 複数 AI のランタイムオーケストレーション(§5 は `team` 定義の記述までで、実行機構は作らない)、コマンドホワイトリスト自動策定(ロードマップD後段)、auth/payment プリセットの中身 | 実装項目が未設計・実案件での実証待ち |

ステージ構成と依存関係:

```
S0 リリース土台の確定(コミット)
 └─ S1 utakata.yaml マスター化(config パース + team/skills スキーマ)
     ├─ S3 フェッチエンジン(arch get + lock + cache)   ← S2 の構造確定に依存
     ├─ S4 SKILLs 解決(.claude/skills/ managed 同期)   ← S2, S3 に依存
     └─ S5 MCP・フック拡張(guide_for_file / config_get)
 S2 utakata_arch_lib 構造確定・内容同期(別リポジトリ、S1 と並行可)
 S6 セッションログ取り込み(log import。独立、いつでも可)
 S7 一般リリース(全ステージ完了後)
```

## S1: `utakata.yaml` のマスター化 — config エンティティと team/skills スキーマ

**目的**: v1.0.0.md §2 の中枢化。現在「`doc init` が書くだけで誰も読まない」`utakata.yaml` を、CLI 全体が参照する一級の設定ファイルにする。

**スキーマ(v1.0.0 確定版)**:

```yaml
# utakata.yaml
schema: 1
project:
  architecture: clean_architecture
  # オプトイン。未指定なら同梱テンプレートを使う(ネットワーク不要)
  knowledge_repo:
    url: "https://github.com/utakata-code/utakata_arch_lib.git"
    ref: "v1.0.0"          # タグ/ブランチ。解決された SHA は utakata.lock に固定
skills:                     # .claude/skills/ に同期する SKILL の有効リスト
  - utakata-structure
  - clean-arch-auditor
team:
  client: "山田さん(要件の決定権者。仕様変更はこの人の合意が必要)"
  developer: "私(アーキテクチャの責任者。コードの最終レビューを行う)"
  ai_agents:
    - id: feature-builder
      role: "実装担当。plan.yaml と層ごとのガイドを読み込みコードを生成する。"
    - id: structure-auditor
      role: "監視担当。utakata check で構造違反を検知して人間に報告する。"
enforcement:
  impl_plan: "on"
records:
  git: commit
lang: ja
```

**実装(ファイルレベル)**:

| 層 | ファイル | 内容 |
|---|---|---|
| domain | `1_entities/config/utakata_config_entity.dart` | `UtakataConfig`(schema/architecture/knowledgeRepo/skills/team/enforcement/records/lang)。`KnowledgeRepoRef`(url, ref)、`TeamDef`(client, developer, aiAgents) |
| domain | `2_repositories/config_repository.dart` | `read(projectDir)` / `exists(projectDir)` のインターフェース |
| infra | `3_repositories/config_repository_impl.dart` | `YamlDataSource.parse` で読む。存在しない・キー欠落はすべて既定値(全フィールド optional) |
| domain | `3_usecases/init_doc_usecase.dart` | 既定テンプレートを新スキーマに更新(`schema: 1`、`skills:`・`team:` はコメントアウト例として同梱) |
| domain | `3_usecases/*` | architecture 解決箇所(apply/check/status/feature add)で `utakata.yaml > plan.yaml > 'clean_architecture'` の優先順位に変更。食い違い時は warning |
| app | `generate_claude_integration_usecase.dart` | `team` が定義されていれば、生成する `CLAUDE.md`(新規: プロジェクト直下に生成)に「登場人物と役割」「doc/ の読み方(summary/plan/records への導線)」節を出力 |
| app | `doctor_usecase.dart` | `utakata.yaml` の schema 検査(未知キー warning、schema>1 はエラー)を診断項目に追加 |

> `CLAUDE.md` 生成は v1.0.0_review.md ⑥追記の「導線を書いておくだけで十分」の実装でもある。既存ファイルがある場合は上書きしない(managed マーカー方式は使わず、存在チェックでスキップ+案内のみ)。

**テスト**: config パース(全省略/全指定/壊れ YAML)、優先順位解決、doctor の schema 検査。

**完了条件**: `utakata doc init` → 新スキーマ生成、`utakata create` → team 入り CLAUDE.md 生成、既存プロジェクト(utakata.yaml なし)でも全コマンドが従来どおり動く。

## S3: フェッチエンジン — `utakata arch get` + lockfile + キャッシュ

**目的**: v1.0.0.md ロードマップB。`knowledge_repo` をオプトイン指定した場合のみ、リモートの arch_lib を取得して利用可能にする。

**挙動仕様**:
- `utakata arch get` — `utakata.yaml` の `knowledge_repo` を読み、`git clone --depth 1 --branch <ref>` で `~/.utakata/cache/<url の sha256 先頭12桁>/<ref>/` に取得。取得後 `git rev-parse HEAD` の SHA を `utakata.lock` に記録。
- `utakata.lock` が既にあり SHA 一致のキャッシュが存在すればネットワークに出ない(冪等)。
- `utakata arch get --update` — ref を再解決し、SHA が変わる場合は新旧 SHA と変更ファイル数を表示して確認プロンプト(注入対策の最小実装)。
- 解決優先順位(既存の local-first を拡張): **①プロジェクト内 eject 済み定義 → ②lock 済みリモートキャッシュ(knowledge_repo 指定時のみ) → ③同梱テンプレート**。
- `knowledge_repo` 未指定なら②が消えるだけで、現在と完全に同じ動作(D2)。

**実装(ファイルレベル)**:

| 層 | ファイル | 内容 |
|---|---|---|
| domain | `2_repositories/knowledge_repository.dart` | `fetch(ref)` / `resolve(lock)` / `cachedPath(sha)` |
| infra | `2_data_sources/2_remote/git_data_source.dart`(新規) | `ProcessDataSource` と同様の `Process.run` ラッパで git clone/rev-parse/diff --stat。git 不在時は `GitNotFoundException` |
| infra | `3_repositories/knowledge_repository_impl.dart` | キャッシュ管理 + lock 読み書き(lock は単純 YAML: url/ref/sha/fetched_at) |
| infra | `3_repositories/architecture_repository_impl.dart` | 解決優先順位②の差し込み |
| app | `1_commands/arch_command.dart` | `arch get` サブコマンド追加 |
| domain | `3_usecases/doctor_usecase.dart` | lock と utakata.yaml の url/ref 不一致、キャッシュ欠落を診断 |

**テスト**: ローカル bare リポジトリを fixture にした clone/lock/冪等性/`--update` の SHA 差分検出。git 不在時のエラーメッセージ。

**完了条件**: `knowledge_repo` 指定プロジェクトで `arch get` → オフラインで `check`/`apply` がキャッシュから動く。未指定プロジェクトの挙動が一切変わらないことをテストで固定。

## S4: SKILLs 解決 — `.claude/skills/` への managed 同期

**目的**: v1.0.0.md §2-C。アーキテクチャ同梱 SKILL と `utakata.yaml` の `skills:` リストを `.claude/skills/` に反映する。

**挙動仕様**:
- `utakata skills sync` — 解決済みアーキテクチャ(同梱 or キャッシュ)の `skills/` から、`utakata.yaml` の `skills:` に列挙された id のみを `.claude/skills/<id>/` へコピー。
- コピーする各ファイル先頭に `<!-- utakata:managed from=<arch|repo>/<id> sha=<コンテンツhash> -->` を付与。
- 同期時の競合規則(D4):
  - マーカー無しの既存ファイル → **絶対に触らない**。警告表示のみ。
  - マーカー有り+コンテンツ hash 一致 → 上書き更新(managed として正当)。
  - マーカー有り+hash 不一致(人間が managed ファイルを編集) → スキップして警告、`--force` でのみ上書き。
- `skills:` から外された managed スキルは削除候補として表示(自動削除はしない)。
- `utakata create` は従来のハードコード2スキルの生成をやめ、`skills sync` を内部呼び出しする形に統一(既定 skills は `utakata-structure` など CLI 側同梱の汎用 SKILL)。

**実装**: domain `3_usecases/sync_skills_usecase.dart`、app `1_commands/skills_command.dart`(新規)、`generate_claude_integration_usecase.dart` の統合。

**テスト**: 3つの競合規則それぞれ、リスト除外時の削除候補表示、create 経由の初回同期。

**完了条件**: 手編集したスキルが `sync` で壊れないことがテストで保証されている。

## S5: MCP・フック拡張 — lint エラー→ガイドの決定論的解決

**目的**: v1.0.0.md ロードマップC。「エラー発生ファイル → 該当レイヤーのガイド」を決定論的に引けるようにし、AI の修正コンテキストに即座に食わせる。

**挙動仕様**:
- `utakata guide for <file> [--json]`(新規) — ファイルパスから feature/層を既存の `NameRuleMatcher`/`ExpectedStructure` 機構で特定し、該当レイヤーのガイド本文(+違反があれば該当命名規則)を返す。パスが features 外なら core 系ガイドへフォールバック。
- `utakata check --quick --json` の出力に `guide_ref`(該当ガイドの layerPath)を追加 — PostToolUse フックの出力だけで、AI が次に `guide_get` を引けるようになる。
- MCP ツール追加(読み取り専用は維持):
  - `guide_for_file` — 上記 usecase をそのまま公開。
  - `config_get` — `utakata.yaml` の内容(team 含む)を返す。AI が「誰に判断を仰ぐか」を機械的に取得できる(§2-B)。
- `guide_get` は S3 の解決優先順位(eject → キャッシュ → 同梱)に自動追従(ArchitectureRepository 経由なので実装変更は小さい)。

**実装**: domain `3_usecases/guide_for_file_usecase.dart`、`guide_command.dart` に `for` サブコマンド、`mcp_server.dart` にツール2件、`check` の JSON 出力拡張。

**テスト**: パス→ガイド解決(features 各層/core/該当なし)、MCP ツールの JSON-RPC 応答。

**完了条件**: `flutter analyze` が報告したファイルパスを `guide for` に渡すと正しい層のガイドが返る e2e 確認。

## S6: セッションログ取り込み — `utakata log import claude-session`

**目的**: v1.0.0.md ロードマップD(再訂正後の確定要望)。Claude Code のセッション生トランスクリプトを人間駆動で `doc/records/` に取り込み、Git 管理下に置く。

**挙動仕様**:
- `utakata log import claude-session [--list | --session <id> | --last] [--full] [-y]`
  - `--list`: `~/.claude/projects/<このプロジェクト>/` 配下のセッション一覧(日時・先頭発言の抜粋)を表示。`<このプロジェクト>` はカレント git リポジトリから Claude Code と同じ規則でパスを導出。
  - 取り込み対象: 既定では **user 発言と assistant のテキスト応答のみ**(thinking・tool_use・tool_result は除外 — ノイズ・肥大化対策)。`--full` で全イベント。
  - **レダクション(既定 on)**: 秘密情報らしい行(`API_KEY=`、`Bearer `、`-----BEGIN ... PRIVATE KEY`、AWS キー形式等の正規表現セット)を検出したら該当行を `[REDACTED]` に置換し、件数を表示。検出ゼロでも取り込み前に**必ずプレビュー(件数・期間・冒頭数行)を表示して確認プロンプト**(`-y` でスキップ)。
  - 保存先: `doc/records/sessions/<YYYY-MM-DD>_<sessionId先頭8桁>.jsonl`。正規化スキーマ `{ts, role: user|assistant, text, session, seq}`(Claude Code 側の内部フォーマット変更から絶縁するため生 JSON をそのまま持たない)。
  - `utakata log render` を拡張し、sessions も `doc/preview/sessions/` に人間可読 Markdown を生成。
- deny ルール(`doc/records/**`)は既にこの領域をカバーしており、AI は読み取り専用のまま(D5)。MCP に `sessions_query` は追加**しない**(まず運用してから判断)。

**実装**: domain `1_entities/record/session_entry.dart`・`3_usecases/import_claude_session_usecase.dart`(パース・フィルタ・レダクションは純関数に分離してテスト可能に)、infra は既存 `JsonlDataSource`/`FilesystemDataSource` を再利用、app `log_command.dart` に `import` サブコマンド。

**テスト**: fixture の偽トランスクリプト(thinking/tool 混在)→フィルタ結果、レダクション正規表現の当たり/外れ、プロジェクトパス導出、`--full`。

**完了条件**: 本リポジトリ自身の実セッションで `--list` → 取り込み → `log render` まで通る(取り込んだファイルはコミットせず検証後削除)。

## リスクと逃げ道

| リスク | 対応 |
|---|---|
| S2 のコンテンツ書き直し(特に mvvm)が最大の作業量。CLI 実装より先に息切れする | S2 を「clean_architecture 先行、mvvm は最低限(構造のみ新形式・文章は簡素)」に分割可。_starter は骨組みだけなら小さい |
| arch_lib 新構造への CLI 追従(S2 の CLI 側)で既存テストが広く壊れる | 同期スクリプトが旧→新の変換を吸収する設計にしたので、CLI 側の読み取り変更は `principles/`+`layers/` のパス差し替えに限定される |
| セッショントランスクリプトの内部フォーマットが Claude Code 更新で変わる | 正規化スキーマに変換して保存する設計(S6)で影響を取り込み時のパーサ1箇所に閉じ込め済み。パース不能イベントは skip+件数報告 |
| `arch get` の git 依存(環境に git が無い) | knowledge_repo はオプトインなので、git 不在は「その機能を使う人だけ」のエラー。メッセージでインストール案内 |

## 推奨実施順

**S0 → S1 → S2 → S3 → S4 → S5 → S6 → S7**(S6 は独立しているので、S2 のコンテンツ作業の合間に前倒し可)。
