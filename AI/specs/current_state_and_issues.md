## 2. 現状の仕様

### 2.1 コマンド体系（v0.5.8）

| 分類 | コマンド | 役割 |
|------|---------|------|
| 生成 | `create <appName>` | Flutter プロジェクト新規作成 + 依存マージ + テンプレート展開 + build_runner |
| 生成 | `feature add <name>` | feature のディレクトリ構造 + GUIDE.md を生成 |
| 生成 | `feature init` | `plan_architecture.yaml` から全 feature を一括生成 |
| 生成 | `core` | `core_modules` 定義から `lib/core/*` を生成 |
| 計画 | `plan` | `feature_request.yaml` → `plan_architecture.yaml` に変換 |
| 検証 | `scan` | `lib/features/` の実構造をスナップショット（`current_structure.yaml`） |
| 検証 | `diff` | 計画 vs 実構造の差分（リアルタイムスキャン） |
| 検証 | `check` | CI 用ヘルスチェック（diff のラッパー、違反で exit 1） |
| 検証 | `validate` | 命名規則・ディレクトリ構造の違反検出 |
| 状態 | `status` | Flutter バージョン + analyze + diff を集約し `project_status.yaml` + `.md` プレビューを出力 |
| 定義 | `arch list / show / export / create` | アーキテクチャ定義の管理 |

### 2.2 テンプレート構成（生成プロジェクトに展開されるもの）

| ディレクトリ | 役割 | 編集想定 |
|-------------|------|---------|
| `AI/architecture/` | arch_definition.yaml + 各層 GUIDE.md + ガイド群 | GUIDE.md 等は**編集不要**、arch_definition.yaml はローカル上書き可 |
| `AI/specs/` | 仕様書・構造計画書・feature_request.yaml | **プロジェクトごとに編集必須** |
| `AI/snapshots/` | CLI が自動生成する状態スナップショット | 手動編集しない（自動生成） |
| `AI/logs/` | 開発者⇔AI の会話ログ | 編集する（追記） |
| `AI/scripts/` | 旧シェルスクリプト（**非推奨**だが同梱され続けている） | 使わない |
| `.agent/` | エージェント向けルール・スキル・ワークフロー | 編集不要 |

アーキテクチャテンプレートは `clean_architecture`（4層）と `mvvm`（3層）の2種。定義は**ローカル優先読み込み**（プロジェクト内 `AI/architecture/` があればそちら、なければパッケージ同梱）。

### 2.3 想定開発フロー（`.agent/skills` の3ステージ）

```
Stage 1 仕様策定 ──→ Stage 2 構造計画 ──→ Stage 3 実装
（application_      （structure_plan.md    （レイヤー順に実装、
 specification.md）   + feature_request.yaml  GUIDE.md 参照、
                      → plan → feature init）  validate/diff で検証）
```

- 登場人物は**開発者と AI の二者**を想定
- モード1（新規開発）のみ実装。モード2/3（既存アプリ）は TODO のまま

### 2.4 実運用（受託案件）で使っている doc/ 構造

テンプレートに存在しない実運用ディレクトリ。現在は**別プロジェクトからコピーした仮配置**で、構造は洗練途上。

| パス | 役割 |
|------|------|
| `doc/案件整理サマリー.md` | 案件の単一情報源（契約条件・機能一覧・合意履歴を日付/金額つきで管理） |
| `doc/archive/見積もり提案書.md` | 契約前フェーズの成果物 |
| `doc/log/raw/` | **お客様との会話**の生ログ（日付別 .md） |
| `doc/log/post_contract_summary_*.md` | 生ログの期間別サマリー（出典行番号つき） |
| `doc/log/impl/` | **feature ごとの実装計画書**（テンプレートあり、完了後 archive/ へ） |
| `doc/guides/` | 案件横断の再利用ナレッジ + 案件固有ガイド（project/） |

> ログの棲み分け（現運用）: `AI/logs/conversation_log.md` = 開発者⇔AI、`doc/log/raw/` = お客様⇔開発者

## 3. 課題

### 3.1 構造・思想レベルの課題（改善テーマ）

#### ① 編集する/しないファイルの区別がない

- テンプレートには「編集不要（ガイド・ナレッジ・アーキテクチャ説明）」と「要編集（feature_request.yaml 等）」の2種類があるが、現在は案件ごとの git に全部入りで、**編集しないほうがいいファイルも変更できてしまう**
- → **別 git 管理 or 読み取り専用化**を検討

#### ② ナレッジとロジックが未分離

- ナレッジは「テンプレート由来（案件非依存）」と「プロジェクト固有」の2層があるが、現在は区別なく混在
- 実案件では `doc/guides/`（store/payment/infrastructure/testing/troubleshooting = 案件非依存、project/ = 案件固有）として自力で分離運用している

#### ③ スナップショット方式は後からの変更に弱い

- `plan` はファイル名をフル指定しない（`__files__` は命名が決定的な場合のみ）
- 生成後にファイルを追加したくなったら **YAML を編集して計画に反映し直す**双方向メンテナンスが発生
- → **`lib/` を常時監視するローカルサーバー**で実構造を動的反映すれば、常に現在の状態が分かり `scan`（スナップショット）自体が不要になる。**これを起点にコマンド体系を再編**する

#### ④ feature ごとの実装計画が仕組み化されていない

- 規模が大きい案件では feature ごとに実装計画を書く運用が実際に発生（現在は `doc/log/impl/` に仮配置）
- → utakata の推奨フローとして **feature 計画後に feature ごとの実装計画作成を強制**する
- 実案件の `_実装計画書テンプレート.md` が下敷き（出典・合意の区別、変更ファイル一覧、utakata diff ゼロ維持を既に規定）

#### ⑤ お客様との会話管理が非構造化

- 現在は日付別の生ログ .md のみ（妥協運用）
- → **JSON/YAML で構造管理 + .md プレビュー生成**（status と同じパターン）。`utakata log add ""` のようなコマンドで日時・発言者・内容を記録
- **役割分担（決定）**: 記録は**人間がコマンドで行う**（お客様との会話は人間しか知り得ないため）。**AI エージェントは読み取り専用** — 構造化されたログを要件・合意の情報源として参照する

#### ⑥ AI エージェント統合が汎用のまま

- `.agent/` は特定エージェント非依存の Markdown 群で、強制力がない
- → **Claude Code 前提**に再整備:サブエージェント定義・スキル・フック（例: コード変更後に validate/diff を自動実行するフック）

#### ⑦ feature の再利用手段がない

- auth / payment など頻出パターンは案件をまたいでほぼコピペなのに、毎回ゼロから実装している
- → **feature 丸ごとのプリセットテンプレート**を用意し、`utakata feature add --template <id>` で生成。既存のローカル優先テンプレート読み込みの仕組みを拡張すれば実現しやすい

### 3.2 テンプレート・フローの乖離（実案件で判明）

| 乖離 | 内容 |
|------|------|
| 当事者モデル | テンプレートは二者（開発者+AI）、実態は三者（+お客様） |
| 契約前フェーズ | 見積もり・提案書のフェーズがテンプレートに存在しない |
| 合意トラッキング | 「いつ・いくらで・何を合意したか」の管理概念がない |
| 記録の二重化 | `AI/logs`（未使用のまま）と `doc/log`（実際の蓄積先）に分裂 |
| 要件の反映経路 | 実要件はお客様⇔開発者の会話にあるが、仕様書への反映が仕組み化されていない |
| Stage 3 の記述 | 非推奨の `AI/scripts/*.sh` をまだ案内している（CLI コマンドに未更新） |

## 4. 再編の方向性（たたき台）

課題③を起点に、コマンド体系を「静的スナップショット」から「動的な状態把握」へ再設計する。

| 現在 | 再編後のイメージ |
|------|----------------|
| `scan`（手動スナップショット） | **廃止** — 常時監視サーバーが実構造を常に保持 |
| `diff` / `check` / `validate` / `status` | 監視サーバーの状態を参照する形に統合・再編 |
| `plan` → YAML 手編集で追従 | 実構造からの逆方向反映も可能に（双方向メンテの解消） |
| （なし） | `utakata log add` — お客様会話の構造化記録（⑤・記録は人間、AI は読み取り専用） |
| （なし） | `utakata feature add --template <id>` — feature プリセット（⑦） |
| （なし） | feature 実装計画の生成・強制（④） |
| `.agent/` 汎用 Markdown | Claude Code のスキル・サブエージェント・フックとして再構成（⑥） |

**未決事項**: 監視サーバーのプロセスモデル（常駐 or オンデマンド）、①の別 git / 読み取り専用の方式、`doc/` と `AI/` の統合後のディレクトリ設計、コマンド再編の優先順位。
